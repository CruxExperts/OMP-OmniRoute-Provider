# Contracts and qualification

OmniRoute source establishes what its handlers do. OpenAPI descriptions help with
schemas, but they do not override actual source behavior. A route inventory entry
is not permission to call that route.

## Reproduce the source inventory

Use the pinned toolchain and immutable source receipt:

```sh
bun run prepare:upstream
bun run scripts/acquire-route-corpus.ts --check
bun run verify:contracts
```

Source preparation verifies the archive checksum before extraction. The collector
checks the source files and framework authorization context against that archive.
Its content-addressed store shares repeated import closures and provenance records;
readers verify each record digest and the expanded manifest digest. Changing the
storage representation does not change the expanded source facts.

The current source pin is OmniRoute v3.8.53 at commit
`191dce8d534ceb56c28a08e71381284a9a87838f`. Its pinned release source asset
is verified by digest; the collector checks the captured source bytes against
that archive. A refreshed source inventory does not itself qualify operations
or make receipts from an earlier source current.

The closure also includes numbered SQL migrations discovered at runtime by the
pinned database migration runner. They are opaque source bytes, verified against
the same archive and included in the route and framework digests. External
migration directories need separate evidence.

The earlier pinned 3.8.52 OpenAPI document has an unquoted comma in the `news` description
for `GET /api/system/version`. The generator records this discrepancy and repairs
only that annotation when the exact source commit, document digest, location, and
malformed value match. It infers no response type or runtime behavior from the typo.
Other unsupported schema keywords still fail verification.

## Qualify behavior independently

Implement the operation contract, strict input checks, authorization domain,
response projection, and reconciliation in their existing owners. Exercise the
actual pinned upstream handler or an independently reviewed source-derived oracle.
A server fixture that calls the client's own validator or normalizer can test
integration, but cannot independently establish that the client matches upstream.
Expected outcomes must not be generated by the client helper under test.

Cover permission failures, invalid input, secret-safe output, and the relevant
mutation lifecycle. Mutation cases include cancellation, expired approval, competing
plans, target changes, credential rotation, duplicate application, and lost responses.
An external writer can race a target reread when the server lacks conditional writes;
document that limit rather than treating the reread as an atomic lock.

Tests write raw observations under ignored task state. Only sanitized, reviewed
reference evidence belongs in `provenance/qualification/`, named by its canonical
content digest. Active eligibility records bind the exact handler, import closure,
framework context, contract, test source closure, and observed result. A changed
source, test, contract, or outcome invalidates the previous qualification.

The test fingerprint includes the complete `package.json` and available Bun
lockfiles, as well as the local import closure. Version and tested-host metadata
changes therefore require fresh receipts even when runtime behavior is unchanged.
Subprocess and dynamic-file consumers declare additional inputs in a sibling
`<source-file>.inputs.json` file with `schemaVersion: 1` and a nonempty `files`
array. Each entry is a unique, normalized repository-relative regular-file path;
private state, dependency trees, symbolic links, and escaping paths are rejected.
The declaration and declared opaque bytes enter the same canonical closure hash as
imports. A changed Python driver or runtime manifest therefore invalidates its
consuming receipt even when the HTTP observation is unchanged. Unrelated cases
without that dependency retain their existing fingerprint.
The source-owned ingress runner uses explicit `--bwrap`, `--node`,
`--source-archive`, `--dependency-dir`, and `--output-dir` paths. Its fixture
manifests bind the exact Node executable, dependency tarballs, source archive,
selected source files, and bubblewrap package. With explicit SHA256 approval,
`--preflight-only --bwrap-stage-dir` downloads only the 56,876-byte Debian
bubblewrap 0.12.0-1~deb13u1 amd64 package, verifies its exact digest, and extracts
only the binary and copyright under `RUNNER_TEMP` in CI. Already-installed
libc6 >= 2.38, libcap2 >= 1:2.10, and libselinux1 >= 3.1~ are required; no
packages or dependencies are installed or upgraded. Without a staged `--bwrap`
or explicit helper approval, preflight fails. On disposable GitHub-hosted Linux
runners, the separate `approve_ci_apparmor` dispatch approval allows a temporary
AppArmor profile attached only to that exact staged executable path. The runner
checks the pinned binary before loading it through the existing `apparmor_parser`
with sudo, records the profile and binary digests, and removes the profile in an
always-run cleanup step. It does not disable AppArmor or change global sysctls.
Missing prerequisites or uncertain load/removal fail the job. The actual
user-systemd, cgroup v2 memory and CPU, namespace, and private loopback checks
still run before any Node, source, or dependency acquisition. Other kernel or
host policy restrictions remain failures; there is no weakened fallback.
`--stage-dir` repeats the full preflight, then stages the
explicitly approved pinned Node archive, source and manifest tarballs. The
runner separately verifies actual isolation and resource readbacks.
Qualification dispatch offers `preflight-only` and `ingress-only` modes before
the full archive and native targets; neither mode creates a qualification receipt.
These build-only inputs are excluded from the runtime npm package and its
TypeScript program. The isolated runner uses the upstream production-default
Next bundler with explicitly verified disposable source overlays and pinned
declaration extractions for the authentication read dependency closure. Original
and executed hashes are retained; the source archive is unchanged. Extracted
API-key validation, encryption/backfill, feature-flag reads, and cache resets
retain their source declarations rather than placeholder exports.
Auth/settings still use bounded fixture storage and selected disposable
`node:sqlite` queries, not native production persistence or the full application.
SSO provisioning SQL and audit writes remain unsupported; a compiled import
does not establish a successful effect or qualify those operations.

The pinned cache-metrics reset function warns and delegates to the metrics read;
it does not reset metrics. Warm fixture observations do not cover cold database
initialization, recovery, migrations, or scheduler effects. Cache metrics and the
database ping therefore remain pending until their cold lifecycle is qualified.

The separate `--real-core` research runner invokes the pinned core and settings
directly in isolated cold and warm processes, without changing the upstream source
or pre-seeding the migration ledger. In the observed cold run,
`ensureDbInitialized` opens and creates the database file before
`getDbInstance` checks freshness. Initialization then seeds migration 001 and
creates `quota_snapshots` inline; the pending migration 221 guard aborts. The
warm process was not reached, so warm behavior is unobserved. This is an upstream
cold-initialization failure, not evidence qualifying database ping or cache
metrics reset; both operations remain pending.

Successful complete ingress runs export one allowlisted `observed-outcomes.json`
with exact input hashes, approved-archive source and declaration identities,
validated executed backend-overlay hashes, isolation checks, and bounded HTTP
outcomes. Authentication flags come from the recorded responses and events;
contradictory denied-case success or usage markers prevent export.
CI uploads only that file, never scratch directories, credentials,
mount tables, events, or private logs. Missing, partial, or contradictory inputs
prevent export. This retained prerequisite is not an operation qualification
receipt; the existing per-operation producer and reviewed eligibility still gate use.

For `GET /api/health`, `GET /api/health/degradation`, the three agent-skills reads,
the five model-combo-mapping operations, and the six qualified combo operations,
a verified eligibility record additionally names a retained
`provenance/qualification/ingress-<sha256>.json` export and its SHA-256 over the
exact file bytes. The generator checks the pinned source archive, proxy and
extracted declaration identities, and the runner's recomputed disposable overlay
identities, as well as declared runner input bytes, runtime, isolation, and the
public HTTP observations before putting the ingress digest in the generated
qualification. For degradation it also checks the exact management denial,
authorized report, summary, recovery and unobserved hosted-failure fields.
The handler observation remains a separate receipt; neither it nor the
research-only ingress export alone qualifies the operation. Missing, mismatched,
or stale ingress evidence fails closed.
The runtime compares the recorded ingress digest with the generated qualification;
it does not independently re-run the ingress experiment.

The public liveness observation additionally checks the timestamp against its
request window, drain error envelope and retry header, request/correlation ID
relationship, recovery, and configured versus unlisted CORS origins. Public
authentication includes separate anonymous observations with the bypass at its
source default and disabled. It does not imply that proxy cache warmup or IP
filtering avoids storage. The IP-filter observation requires the configuration
read and forwarded-address rejection and recovery, with request ID and CORS
evidence. It covers an unstamped, unknown peer; it does not prove authenticated
socket-peer stamping or proxy trust. Changed runner inputs require a new isolated
build and HTTP observation before acceptance.

Canonical API response metadata includes source-witnessed pipeline draining and
IP-filter rejection branches before route policy evaluation. This does not
qualify an operation or prove exclusive response shapes: another applicable
policy or handler may return the same status with a different body or headers.
HEAD, OPTIONS, dynamic paths, and rewritten aliases need their own method/path
proof rather than inferred JSON outcomes.

Failed isolated runs retain only `failure.json`: an allowlisted stage and error
class, exit code or signal, and source/runtime/tracked-input digests. CI uploads
that exact file when present, never the private compiler or HTTP logs.


After the final manifest edits, rerun every suite named by the active eligibility
records. Compare each fresh observation and source binding with its reviewed
reference before updating any receipt. An unchanged observation may be rebound
to the current test fingerprint in a new content-addressed record; retain the
old record and review any behavioral difference separately. Update eligibility
references and regenerate the operation inventory before running the checks below.

After tests run, compare fresh observations and check deterministic output:

```sh
bun run verify:qualification
bun run scripts/acquire-route-corpus.ts --check
bun run verify:contracts
bun run docs:check
```

The raw agent-skill handler also has a disposable-filesystem check for its
Markdown body, cache/source headers, missing catalog ID, and sanitized handler
errors. The direct invalid-parameter checks are not HTTP ingress evidence.
GitHub fallback fetching and its upstream-failure response remain unobserved;
this check does not qualify `GET /api/agent-skills/{id}/raw` or change its

Active qualification is being rebuilt for the current source and mutation-safety
contract. Earlier evidence for fallback chains, capability overrides, provider
aliases, and provider configuration is historical; it cannot authorize the new
candidate. Source-backed fixture checks do not by themselves restore eligibility
or prove clean framework ingress. Combo metrics retain the pinned source's separate
fallback-request count and skips-per-request fields. Held mutations still require
their available dependency reads and independent effect evidence. The
[generated inventory](generated.md#operation-inventory) owns the current counts.

Combo mutation preflight reads the complete collection with both pagination keys
omitted, checks its row count and unique identities, and rejects oversized or
incomplete responses before selecting targets. Duplicate and probe plans also
bind the exposed auto-combo and provider catalogs. These reads detect observable
drift; they do not lock external writers or expose cloud settings, key grants,
proxy assignments, or all provider state. Mutations retain unknown settlement
where hidden effects cannot be independently observed. The loopback probe fixture
does not qualify a real charged provider request or restore active eligibility.

Pinned-source checks show that selected and default auto-combo GET responses do
not include the capability resolution used by duplicate POST. Changing model
capabilities can change the duplicate's normalized weights without changing
either GET response. These reads therefore do not establish capability-resolved
duplicate-target equivalence; duplicate qualification must not rely on that
assumption.

The ingress producer separately records six exact combo method/path cases:
collection, item, auto, builder options, metrics read, and metrics reset. These
use the existing management reachability control in place of each route body.
They bind original source digests and prove framework policy routing only;
the actual handler outcomes must come from the independent pinned combo suite.
Changing the producer invalidates every receipt bound to its prior input bytes.

The capability-overrides GET ingress observation likewise covers management-policy
denial and authorized reachability through a replacement control. It does not
execute the real handler, establish persistence behavior, or qualify PATCH or
DELETE; independent source-handler observations remain required.

Approval-state checks and outcome reconciliation have separate responsibilities.
Read and bind the relevant target state that upstream exposes, even when a
later read cannot prove whether a lost-response mutation completed. An upstream
visibility limit alone must not prevent a supported operation. Record that
limit in the source-bound contract and show it alongside the operation's exact
scope and observed state in the confirmation. This does not excuse an unfinished
client read, a failed available read, or omitted observable routing dependencies.
A missing target row cannot prove that all dependent cleanup succeeded.

For example, a metrics reset can cover all counters for the selected combo even
when upstream omits some counter values from its GET response. Read and bind the
exposed metrics, disclose that hidden counters are also cleared, and retain an
unknown outcome when complete success cannot be established. A reset of all
metrics also stops upstream's periodic cleanup timer until the module reloads;
that consequence belongs in its confirmation. Neither a partial observation nor
a successful HTTP response should be presented as proof of complete state.

The migration also distinguishes a response that proves complete success from
one that requires verified postconditions or leaves an unknown outcome. A
dispatched error can follow partial writes. Neither an HTTP success status nor
a server error alone establishes the complete result of a cascading operation.
Unknown outcomes must never trigger an automatic replay.

The version 3 contract binds these decisions in `mutationSafety`. Its `preflight`
contains named observations, an evidenced reason that target reads do not apply,
or an explicit unavailable dependency. Its `reconciliation` either names all
required postconditions or declares an unknown outcome. `settlement` lists only
response statuses independently proven to acknowledge every required effect.
Legacy contracts cannot authorize mutations. Pagination without a verified
complete-read contract remains blocked; a partial page cannot prove absence.

For the source-qualified mapping collection read, `unpaginated-list` requires
omitted pagination inputs, a raw row count matching the source's total, unique
identities, and bounded response size before selecting a target. It does not
implement page traversal. Incomplete, duplicate, oversized, or paginated results
cannot be used to approve a mutation or establish absence.

An empty active eligibility list is a valid fail-closed development state. It does
not satisfy release acceptance. Historical qualification is retained separately
when a new source release invalidates its bindings.

## Release acceptance

Every applicable operation needs qualification. A source-justified exception needs
its source evidence and reason; unfinished work is not an exception. Each of the
eight native OMP targets must also test the same final package archive. See the
[release guide](release.md) for receipt and publication requirements.
